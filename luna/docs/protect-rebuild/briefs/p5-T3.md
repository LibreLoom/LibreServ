## 2. Which rows get it (DriveFileExplorer)
- Query `["private-backups-mine"]` → `GET /api/v1/private-backups/mine` (only for a signed-in non-guest user; `retry: false`; an error just means no badges).
- A dir row gets `notBackedUp` when the explorer's `driveId` and the row's full path match an item in `items` (compare `drive_id`, and the path with leading/trailing slashes trimmed on both sides) and `drive_backups === 0 && !cloud_backup`.
- Both `ProtectButton` sites (~817 row actions, ~1039 header) pass it.
- Invalidate `["private-backups-mine"]` wherever the explorer already invalidates backup queries after the Protect sheet closes; if it doesn't, add `queryClient.invalidateQueries({ queryKey: ["private-backups-mine"] })` in the sheet's `onClose` handler at ~1409.
- Only the owner sees it (the API returns only the caller's items).

## 3. Open a Backups folder from a link
`/drives/<id>?backups=1` opens that drive's Backups folder: on mount (and when the param changes) `if (searchParams.get("backups") === "1" && !guest) setBackupsDriveId(driveId)`. When the person leaves the Backups folder (`onExit` ~928), remove the param with `setSearchParams` (replace, no new history entry). `DriveFileExplorer` is also used by `PublicSharePage.jsx`: there `guest` is true, so nothing happens; confirm `useSearchParams` is safe there (it's inside the same Router).
