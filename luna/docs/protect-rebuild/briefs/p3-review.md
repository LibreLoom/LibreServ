## Blocker

### B1. Luna restore downloads the whole backup while holding the global DB lock, so a real-size restore breaks end to end
- `luna/crates/lunad/src/api/cloud_restore.rs:181-185` takes `db.lock()` and then calls `restore_with_store`. That calls `recover::rebuild_snapshot_index` (`luna/crates/lunad/src/backup/cloud/recover.rs:50-65`), which does every network read under the lock: `list_records`, `get_record`, `get_pack` of every tree pack. Worse, `index_tree_chunks` (`recover.rs:192-196`) calls `store.get_pack` on **every data pack** only to learn its size.
- What goes wrong: an Admin restores a 500 GB backup and Luna downloads all 500 GB while holding the one DB mutex. Every other API call (sign-in, files, settings) hangs for hours. The browser's POST also outlives any proxy timeout (the Connect tunnel or Cloudflare is about 100 s). `restoreFromPhrase` then throws, so `savePhrase` (`luna/web/src/lib/cloudRestore.js:56-63`) never runs and the person's old phrase is never re-linked. The card shows "Could not bring back your cloud backups", while the blocking task carries on in the background and later finishes. The account is also billed egress for the whole backup. The plan lists "downloads every data pack" and "holds the DB lock" as known limits, but this end-to-end failure was not recorded, and it breaks the repo's never-hold-the-lock rule.
- Fix (Haiku-able, two parts):
  1. In `recover.rs` `index_tree_chunks`, stop downloading data packs. Delete the `store.get_pack(&chunk.pack)` line and insert the pack row with `size` set to the largest `chunk.offset + chunk.len` seen for that pack in this tree, as a lower bound. Add a comment saying cleanup and usage treat that number as an estimate. Update the recover.rs tests that assert data-pack sizes.
  2. Split `rebuild_snapshot_index` into `fetch_recoverable(store, identity, keys) -> Vec<Prepared>` and `write_recovered(conn, prepared, now) -> Recovered`. The first takes no `Connection`: it lists and gets records, verifies the signature and luna_id, matches the key, gets the tree pack, opens it, checks the tree hash, and decrypts the tree and meta. The second does only the SQLite work that `index_one` does now (from `already_indexed` through `tx.commit()`). In `cloud_restore.rs::restore`, call `fetch_recoverable` before `db.lock()`, then lock and call `write_recovered` plus the `old_user_ids` remap. Keep the `skipped` counts the same, and make the existing tests call the new pair.

## Major

### M1. Share links let anyone who has the link run up the account's egress bill with no limit
- `luna/connect/internal/api/handlers/share_links.go:241-249` (`Pack`) → `cloud_read.go:368-373` `billing.RecordEgress(d.DB, s.AccountID, n)`. A share token works for 7 days with no per-link byte cap and no rate limit.
- What goes wrong: the link is forwarded or leaked (by email, chat or a screenshot). The link alone opens nothing, but anyone holding it can call `GET /api/v1/share/packs/{id}` in a loop. Each call re-serves a 32 MiB pack that is in scope, and every byte is billed to the household's account.
- Fix: add `egress_bytes INTEGER NOT NULL DEFAULT 0` to `share_links` in both schemas (SQLite and Postgres). In `ShareLinkHandler.Pack`, before `writePack`, read the link's `egress_bytes`. If it is over a cap, answer 429 with `"This link has reached its download limit. Ask the person who sent it for a new one."`. The cap is `3 × (SUM(size) of storage_packs for the link's luna_id)`, or a fixed 2 TB if that is simpler. After a successful copy, `UPDATE share_links SET egress_bytes = egress_bytes + ? WHERE id = ?`. Return the link id from `resolveShare` (it already does) and pass it through. Add a Go test that sets `egress_bytes` over the cap and expects a 429.

### M2. `packAllowed` re-reads every snapshot blob from the store on every pack request through a share link
- `luna/connect/internal/api/handlers/cloud_read.go:252-299`. For each pack GET it calls `loadRecords(d, s, "snapshots")`, which does one `Store.Get` per snapshot (each one a B2 GET), then one SQL query per snapshot.
- What goes wrong: a backup has 200 versions and its folder zip needs 300 packs. That is 60,000 B2 reads and 60,000 SQL queries, so downloads through share links slow to a crawl and B2 transaction costs grow quickly.
- Fix: compute the allowed scope set once per link and cache it. Add a package-level `sync.Map` keyed by link id, holding `{scopes map[string]bool, at time.Time}` with a 60 s TTL. `packAllowed` takes the link id: on a cache hit it uses the stored set, on a miss it computes as now and stores the result. Revoke and expiry stay safe because `resolveShare` runs first on every call. Alternative (no cache): replace the per-snapshot loop with one query, `SELECT DISTINCT scope FROM storage_packs WHERE account_id=? AND luna_id=? AND id IN (<tree pack ids>)`. The snapshot blobs must still be read for protection_id, so the cache is the better fix.

### M3. Re-linking an old account is not proven and only works for the first Admin who restores
- `luna/crates/lunad/src/api/cloud_restore.rs:260-273` hands every `protections.created_by = old` row to the caller for any `old_user_ids` the browser sends. There is no auth-key challenge. Plan §5 step 4 says re-linking happens "by public key, after signing a challenge with their auth key". The route is Admin-only, and the card hides once `needed` is false (`CloudRestoreCard.jsx:140`). So a Member, or a second Admin who later makes a new account and has their old phrase, has no way to re-link: their old backups stay ownerless for good.
- Fix: (a) In `RestoreBody`, add `signature: String` (base64), signed over a challenge from the existing `POST /api/v1/cloud/phrase/challenge` with the phrase's auth secret, domain `"phrase-check"`. In `restore_with_store`, load and verify the signed `users/list` from the store with `keys::verify_user_list(&bytes, &identity.public(), identity.luna_id())`. For each `old` id, look up its `auth_public` in that list and keep `old` only if `crypto::verify(&auth_public, CHECK_DOMAIN, &challenge, &sig)` passes. Use `take_challenge(&user.id, now)` (make it `pub(crate)` in cloud_phrase.rs). In `cloudRestore.js`, fetch the challenge before the POST and sign it with `derive(entropy, lunaId).authSecret`, the same way `cloudPhrase.js:70` does. (b) Split re-linking from the index rebuild: add `POST /api/v1/cloud/restore/relink` (any signed-in user, same challenge check, remaps only to the caller), and show a "Link my old backups" row in the RecoveryPhraseCard for any user whose phrase opens copies under another id. If (b) is out of scope for phase 3, do (a) and note (b) in the plan as phase 5 work.

### M4. Unlinked-Luna notice says the files stay, but they are now deleted after 30 days
- `luna/connect/web/src/pages/BackupsPage.jsx:148-152`: "These files are from a Luna that is no longer linked to this account. The monthly bill stays until you turn payment off." Since this phase, unlinking sets `luna_ids.purge_after` (`device.go:189-191`) and `purgeUnlinkedLunas` deletes the storage. The notice breaks the "Be true" rule, and an Admin reading it would not download in time.
- Fix: in `cloud_read.go` `ListLunas`, also select `l.purge_after` and return it as `"purge_after": int64` (0 = none). In BackupsPage, when `chosen.linked === false && chosen.purge_after > 0`, show: `These files are from a Luna that is no longer linked. They are deleted on ${formatWhen(purge_after)} unless you link it again. Download anything you need before then.` Update `TestCloudListLunas` to assert the field and BackupsPage.test to assert the sentence.

### M5. The "one person's backups" link reaches more than the copy says
- `BackupsPage.jsx:168-176` puts the share button on a **starter group** (people grouped by who started the backup) with `value = part(startedBy)`. Connect's user scope (`cloud_read.go:232-246`) reaches every backup that person has a latest-version key copy for. `SharePage.jsx:45` then shows all of them. For an Admin, that is every shared backup on the Luna, because Admins are on every list. `ShareLinkButton.jsx:164` says "can download **these** backups", and the button sits under the group, so it reads as only that group's backups. This breaks the "Be true" rule, and the Admin may share far more than they meant to.
- Fix: change the user-scope sentence to `Anyone with this link and ${label}'s recovery phrase can download every backup ${label} can open, for 7 days. The link alone opens nothing.`. Optionally add an InfoHint: `For an Admin, that is every shared backup on this Luna.`. Update ShareLinkButton.test.

## Minor

1. **Device name leaks across accounts.** `cloud_read.go:73-76` (`ListLunas`) and `share_links.go:214-219` (`Info`) join `devices d ON d.id = l.device_id` without checking the account. If the device was re-bound to another account, account A sees the name account B gave it. Fix: `LEFT JOIN devices d ON d.id = l.device_id AND d.account_id = l.account_id` in both queries.
2. **Partial downloads are never billed.** `cloud_read.go:371-373` records egress only when `err == nil`, so a client that drops the connection gets bytes for free (this matters together with M1). Fix: `if n > 0 { billing.RecordEgress(...) }` whatever `err` is.
3. **Purge race.** `retention.go:321-342` reads due Lunas and then purges them. A Luna that calls in between gets its storage deleted just after `keepLuna` cleared the flag. Fix: in `purgeStorage`, when `lunaID != ""`, first run `UPDATE luna_ids SET purge_after = -1 WHERE account_id=? AND luna_id=? AND purge_after > 0 AND purge_after <= ?` and abort if 0 rows changed. `keepLuna` then must not clear `-1`: change its WHERE to `purge_after > 0`.
4. **Luna card with no identity.** `cloudRestore.js:43` / `CloudRestoreCard.jsx:117`: when Luna has no identity, `signing_public` is null, `fromBase64(null)` decodes `"null"` to 3 bytes, and the person sees SIGNING_MISMATCH ("doesn't match"), which is misleading. Fix: in CloudRestoreCard, if `!restore.data.signing_public`, render a PageNotice `Luna hasn't found its backup signing key yet. Connect the drives that were in this Luna, then reload this page.` instead of the form.
5. **Plural.** `CloudRestoreCard.jsx:156` renders "1 versions are in the cloud". Fix: pluralize both counts ("1 version is", "N versions are").
6. **Dedup key never checked on restore.** `cloud_restore.rs:214` accepts a 32-byte `dedup_key` without checking it. A recovered version's dedup key feeds `check.rs:420` scope derivation. Fix: in `index_one`, check `hex(&crypto::chunk_id(&dedup, b"luna-scope-v1")[..16]) == hex(&pack.scope_id()[..16])` and skip the snapshot if they differ. This also proves the dedup key matches the tree pack.
7. **Pack cache too small.** `luna/connect/web/src/lib/cloudDownload.js:246` uses a pack cache of 3 while files are read in path order, so a folder whose files share packs out of order fetches the same 32 MiB pack several times, and each fetch is billed egress. Fix: in `downloadFolder`, sort `under` by `entry.chunks[0]?.pack` (then path) before reading, keep zip order by building `files` back in the original order, or raise `keep` to 6.
8. **Download can be cancelled.** `luna/connect/web/src/lib/download.js:9` calls `URL.revokeObjectURL` right after `a.click()`, which can cancel the download in Safari and older Firefox. Fix: `setTimeout(() => URL.revokeObjectURL(url), 60_000)`.
9. **Zip entry names are not cleaned.** `zip.js:107` writes `file.path` as is. Tree paths are signed by Luna, so the risk is small, but a defensive strip helps. Fix: in `downloadFolder`, before zipping, drop any entry whose relative path contains a `..` segment, starts with `/`, or contains `\`.
10. **Phishing host is not an InlinePill.** `UnlockCard.jsx:353` draws the host as a hand-made `font-mono` pill span. Connect web now depends on `@libreloom/ui`, so use `InlinePill` from `@libreloom/ui/components/common/InlinePill.jsx` (AGENTS.md "Names and literals in copy wear a pill").
11. **Unclear backup-scope copy.** `ShareLinkButton.jsx:165`: "the recovery phrase of someone who has Photos" is unclear. Fix: `Anyone with this link and the recovery phrase of someone who can open ${label} can download it for 7 days. The link alone opens nothing.`
12. **`self` records are not filtered for share links.** `cloud_read.go:213-217` returns every `self` record to share links. The data is harmless (encrypted), but it shows how many users have a phrase. This is acceptable, but noted.
13. **`needed` is a plain count compare.** `cloud_restore.rs:139` uses `needed = cloud > indexed`. A snapshot record uploaded before its local row is committed, or private snapshots in phase 4 that the Admin can't open, make the card ask for the phrase on a healthy Luna. Fix later (phase 4): compare snapshot ids, and count only records whose protection is not private.
