# Durable Instruction Files and Context Engineering as an Alternative to Memory Systems in Coding Agents

Research cutoff: November 2026. Note on source quality: vendor docs and engineering blogs are labelled as best-practice opinion; two 2026 empirical papers and the long-context papers are labelled as measured evidence. Web search was unavailable (HTTP 402), so discovery used DuckDuckGo HTML plus direct fetching of primary sources.

## Q1: What guidance do vendors and practitioners give for writing effective AGENTS.md / CLAUDE.md / rules files, and is there evidence these improve agent performance?

### Takeaway

Vendor guidance is consistent and detailed: keep instruction files short, specific, non-redundant, and organized, with executable commands and hard boundaries. Measured evidence is much thinner and genuinely mixed — one 2026 paired study found large efficiency gains but did not measure correctness, while a more rigorous 2026 study found no general success-rate gain and a 20%+ inference-cost penalty.

### Cited Findings

- AGENTS.md is an open, tool-neutral "README for agents" format adopted by 60,000+ open-source projects, supported by Codex, Cursor, Google Jules, Aider, opencode, Zed, Gemini CLI, GitHub Copilot, Devin, Windsurf and others, and now stewarded by the Agentic AI Foundation under the Linux Foundation — [agents.md](https://agents.md/)
- Recommended AGENTS.md content: project overview, build and test commands, code style, testing instructions, security considerations, commit/PR rules; "anything you'd tell a new teammate belongs here too" — [agents.md](https://agents.md/)
- Conflict and precedence rules are explicit in the standard: "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything"; large monorepos should use nested files (the main OpenAI repo reportedly has 88 AGENTS.md files) — [agents.md](https://agents.md/)
- Anthropic's current memory docs (code.claude.com, 2026): target **under 200 lines per CLAUDE.md** — "Longer files consume more context and reduce adherence"; write concrete rules ("Use 2-space indentation", not "Format code properly"); organize with headers and bullets; contradictions mean "Claude may pick one arbitrarily"; `/doctor prompt-audit` detects instructions written for older models, dead file/command references, and conflicting files — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Claude Code best-practices post (published Apr 18 2025, moved to docs Jan 26 2026): "Your CLAUDE.md files become part of Claude's prompts, so they should be refined like any frequently used prompt"; a common mistake is "adding extensive content without iterating"; Anthropic sometimes runs CLAUDE.md through a prompt improver and adds "IMPORTANT"/"YOU MUST" emphasis to improve adherence — [Anthropic Engineering](https://www.anthropic.com/research/claude-code-best-practices)
- GitHub's analysis of 2,500+ agents.md files (Nov 19 2025, updated Nov 25 2025) found a consistent pattern: put executable commands early (with flags), prefer one real code example over three explanatory paragraphs, cover six areas (commands, testing, project structure, code style, git workflow, boundaries), and use three-tier boundaries ("Always do / Ask first / Never do"); "Never commit secrets" was the most common helpful constraint; start simple and add detail when the agent makes mistakes — [GitHub Blog](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/)
- Thoughtworks' context-engineering primer (Birgitta Böckeler, Feb 5 2026) distinguishes "instructions" (do this task) from "guidance" (general rules), recommends building rules files gradually rather than dumping everything up front, notes "there are no unit tests for context engineering", and warns of an "illusion of control" — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html)
- **Measured evidence, study A:** Lulla et al., "On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents" (arXiv:2601.20404, v1 Jan 28 2026; JAWs 2026). 10 repositories, 124 pull requests, OpenAI Codex with gpt-5.2-codex, paired within-task design in isolated Docker containers, repo reset to pre-merge commit. Median wall-clock time fell from 98.57s to 70.34s (**−28.64%**), mean from 162.94s to 129.91s (−20.27%); median output tokens fell from 2,925 to 2,440 (**−16.58%**), mean from 5,744.81 to 4,591.46 (−20.08%). Time and output-token differences were statistically significant (Wilcoxon signed-rank, p<0.05); input tokens changed little at the median. The authors say task-completion behaviour was "comparable", and a 50-task manual sanity check found non-empty, non-trivial changes — [arXiv:2601.20404](https://arxiv.org/abs/2601.20404)
- **Measured evidence, study B:** Gloaguen, Mündler-Sasahara, Müller, Raychev & Vechev (ETH Zurich / LogicStar.ai), "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" (arXiv:2602.11988, v1 Feb 12 2026, v3 Sep 29 2026). Built AGENTbench: 138 instances from 12 Python repositories with developer-committed context files, filtered from 5,694 PRs, plus SWE-bench Lite with LLM-generated files; agents were Claude Code (Sonnet 4.5), Codex (GPT-5.2, GPT-5.1 mini), Qwen Code (Qwen3-30b-coder). Abstract conclusion: "providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average", holding across models, agents, and both generated and developer-committed files; instructions in the files were "well followed", but "repository overviews, although popular and recommended by model providers, are not helpful"; context files are "useful for specifying non-standard coding practices", but any attempt to improve performance "should be rigorously evaluated before deployment" — [arXiv:2602.11988](https://arxiv.org/abs/2602.11988)
- Secondary reporting on the ETH paper's earlier version gives a more differentiated picture: human-written files +4% success on average, LLM-generated files −0.5% on SWE-bench Lite and −2% on AGENTbench (DAIR.AI's summary) or −3% with +20–23% cost (Vaughan's summary); agents followed instructions faithfully (e.g. `uv` usage jumped to 1.6 times per instance versus <0.01 without the file), ran more tests and explored more, but "thorough exploration isn't the same as correct exploration". When README/docs files were removed before generating context files, LLM-generated files improved 2.7% and outperformed human-written ones, implicating redundancy as the mechanism — [DAIR.AI](https://academy.dair.ai/blog/agents-md-evaluation); [Vaughan](https://codex.danielvaughan.com/2026/04/13/what-eth-zurich-paper-gets-wrong-right-about-agents-md/)
- Cost is a consistent finding across both camps: context files add roughly 14–22% more reasoning tokens, 2–4 extra steps, and 20%+ inference cost regardless of file quality — [arXiv:2602.11988](https://arxiv.org/abs/2602.11988); [DAIR.AI](https://academy.dair.ai/blog/agents-md-evaluation)
- OpenAI's Codex guidance (as cited by Vaughan) recommends short files and enforces a `project_doc_max_bytes` default of 32 KiB; when the combined AGENTS.md chain exceeds it, the furthest files are silently dropped — [Vaughan citing OpenAI Codex docs](https://codex.danielvaughan.com/2026/04/13/what-eth-zurich-paper-gets-wrong-right-about-agents-md/) (secondary citation; primary docs not fetched)

### Inferences

- "Improve performance" must be split into **efficiency** (one controlled study found substantial gains) and **correctness** (the more rigorous study found no general gain). Vendor claims of better outcomes rest mostly on experience, not ablation.
- Vendor/practitioner advice and the empirical mechanism agree: encode non-inferable, non-redundant facts (custom commands, unusual tooling, constraints); omit architecture overviews and anything already in the README. The ETH paper found overviews useless even though providers recommend them.
- Only two controlled studies exist, both from 2026, both narrow (small PRs; Python repos; one or a few agent harnesses). The evidence base is emerging rather than settled.
- The two studies are not strictly contradictory: they optimize different outcomes (time/cost versus issue-resolution success) and use different file populations.

### Gaps

- No replication across languages beyond Python, large refactorings, multi-module changes, or multiple agent families in one design.
- No long-term (months) measurement of file quality drifting or of cumulative team benefit.
- The exact magnitude of the "human-written +4%" effect in the current v3 of the ETH paper is unclear; v3's abstract is more negative than earlier versions' secondary summaries — a version-drift conflict worth flagging.
- No source found quantifying the often-repeated "35–55% fewer agent-generated bugs" adoption statistic beyond a secondary research site cited by Vaughan.

## Q2: What are the documented limitations — context window pressure, "lost in the middle", instruction decay, conflicts, staleness, and re-injection cost?

### Takeaway

Limitations split cleanly into two mechanisms: authoring problems (vagueness, contradiction, staleness, redundancy) that auditing can fix, and attention-economy problems (context pressure, position effects, re-injection on every turn) that a static always-loaded file cannot fix. Vendors have responded by building lazy-loading tiers, which is an implicit admission that "inject everything every session" does not scale.

### Cited Findings

- "Claude treats CLAUDE.md files as context, not enforced configuration"; content is delivered as a user message after the system prompt and "there's no guarantee of strict compliance, especially for vague or conflicting instructions". For hard blocking, use PreToolUse hooks or managed settings `permissions.deny` instead — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Size limits are explicit: target under 200 lines per CLAUDE.md ("Longer files consume more context and reduce adherence"); imported `@path` files are expanded and load **together** with the importing file, so imports organize but "don't reduce its context cost"; files over 4 MiB are skipped entirely; auto-memory's `MEMORY.md` index loads only its first 200 lines or 25 KB, and content past the limit is dropped on the next load — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Lazy-loading exists precisely to avoid always-on cost: path-scoped `.claude/rules/` load only when matching files are opened; skills load on invocation or perceived relevance; subdirectory CLAUDE.md/AGENTS.md load on demand. The docs note rules "load into context every session or when matching files are opened", and that skills are for instructions that "don't need to be in context all the time" — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Conflict handling is probabilistic, not deterministic: "if a user rule and a project rule conflict, Claude may follow either one"; "if two instructions contradict each other, Claude may pick one arbitrarily"; conflicts with built-in commit/PR guidance require disabling built-ins via `includeGitInstructions` — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Staleness is a recognized failure class with a dedicated tool: `/doctor prompt-audit` looks for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other"; the AGENTS.md standard says "Treat AGENTS.md as living documentation" — [Claude Code memory docs](https://code.claude.com/docs/en/memory); [agents.md](https://agents.md/)
- Measured cost of compliance: +20%+ inference cost, +14–22% reasoning tokens, 2–4 extra steps per task even when files help — [arXiv:2602.11988](https://arxiv.org/abs/2602.11988); [DAIR.AI](https://academy.dair.ai/blog/agents-md-evaluation)
- **"Lost in the Middle":** Liu et al., "Lost in the Middle: How Language Models Use Long Contexts" (arXiv:2307.03172, v1 Jul 6 2023, v3 Nov 20 2023; accepted at TACL). On multi-document QA and key-value retrieval, performance is "often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle of long contexts, even for explicitly long-context models" — [arXiv:2307.03172](https://arxiv.org/abs/2307.03172)
- **Context rot:** Chroma technical report (Hong, Troynikov & Huber, Jul 14 2025), 18 LLMs including GPT-4.1, Claude 4, Gemini 2.5, Qwen3. Performance degrades with input length even on deliberately simple tasks; lower needle–question similarity degrades faster; even one distractor reduces performance and four compound it; **logically structured** haystacks perform worse than shuffled ones across all 18 models; "structural coherence consistently hurts model performance". On LongMemEval, focused prompts averaging ~300 tokens substantially outperform full ~113k-token prompts across every model family; authors expect real-world tasks to degrade more than their controlled tasks — [Chroma Research](https://research.trychroma.com/context-rot)
- Related long-context benchmarks cited there: NoLiMa (non-lexical needle matching; Modarressi et al., arXiv:2502.05167), AbsenceBench (models fail to notice what is missing; arXiv:2506.11440), MRCR, Latent List, Graphwalks; the report notes NIAH's near-perfect scores created a false impression that long context is "largely solved" — [Chroma Research](https://research.trychroma.com/context-rot)
- Anthropic's canonical context-engineering post (Sep 29 2025) adopts context rot as the framing: context is "a finite resource with diminishing marginal returns", models have an "attention budget", transformer attention creates n² pairwise relationships so capacity is "stretched thin", producing "a performance gradient rather than a hard cliff"; "context pollution" persists at all window sizes; the goal is "the smallest possible set of high-signal tokens". It explicitly notes Claude Code's CLAUDE.md files are "naively dropped into context up front" while glob/grep retrieve files just in time — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Concrete in-session pressure numbers from Anthropic's cookbook (Mar 20 2026): an agent reading eight ~40K-token documents reaches 335,279 tokens; file-read results occupy ~96.3% of final context, first document buried under hundreds of thousands of tokens; prefill latency scales with context length; on a 200K window the same run hard-stops at turn 3 (168,242 tokens) — [Claude Cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)
- **Instruction decay over long sessions:** no direct study found, but adjacent measured evidence: compaction is lossy ("overly aggressive compaction can lose subtle but critical context whose importance only becomes apparent later"), and Anthropic's long-running-agent report (Nov 26 2025) states that compaction "isn't sufficient" — even Opus 4.5 in a loop on the Agent SDK with a high-level prompt "will fall short of building a production-quality web app"; failures include one-shotting and prematurely declaring the job done — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [Anthropic Research](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- The "illusion of control": people say context features "ensure it does X" or "prevent hallucinations", but "as long as LLMs are involved, we can never be certain of anything"; copying others' setups causes duplicated or contradictory instructions — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html)

### Inferences

- A static instruction file is optimized for *stable, always-true, team-shareable* facts. Every one of its documented failure modes gets worse as the file grows, yet growing it is the natural response to new corrections — a structural tension.
- "Lost in the middle" and context rot mean that simply adding more guidance can reduce adherence to the guidance already present; position and relevance dominate volume.
- The vendor ecosystem's answer (rules with `paths`, skills, subagents, compaction, memory) is effectively a set of retrieval and caching layers around instruction files, i.e. context engineering rather than a larger instruction file.
- Conflicts and staleness are human-process problems; no automatic resolution exists beyond audits and version control.

### Gaps

- No direct experiment measuring decay of *adherence to a fixed instruction* over a long session or across context resets.
- No quantitative "staleness half-life" data for instruction files.
- No measurement of cumulative multi-session token cost of re-injecting instruction files (only per-task percentage increases).
- No source found isolating whether position effects apply to system/instruction context specifically versus retrieved content in coding-agent sessions.

## Q3: What does research on context engineering / in-context learning say about how much and what kind of context actually helps, and about long-context degradation?

### Takeaway

The research direction is unambiguous: relevance, position, and signal density beat volume. Focused ~300-token context beats 113k tokens of "full history"; beginning/end positions beat the middle; redundant overviews and distractors actively hurt. "Just-in-time" retrieval with progressive disclosure is the leading alternative to pre-loading, though it trades speed for precision.

### Cited Findings

- Anthropic defines context engineering as "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference" and context as "the set of tokens included when sampling"; it is iterative, unlike one-shot prompt writing — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Right-altitude principle: system prompts must be "specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics"; avoid both brittle hardcoded if-else logic and vague guidance that "falsely assumes shared context". Use sections/XML tags/Markdown headers; start with a minimal prompt and add instructions/examples based on observed failures. "Minimal does not necessarily mean short" — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- On in-context examples: few-shot examples remain "a well-known best practice that we continue to strongly advise"; teams should "curate a set of diverse, canonical examples" rather than "stuff a laundry list of edge cases into a prompt" — for an LLM, "examples are the 'pictures' worth a thousand words" — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Just-in-time" context: maintain lightweight identifiers (file paths, stored queries, web links) and load data at runtime via tools; enables progressive disclosure (file size, naming, timestamps as signals) and keeps only what is needed in working memory; trade-off is that runtime exploration is slower than pre-computed retrieval and needs good tools/heuristics, otherwise the agent "can waste context by misusing tools, chasing dead-ends". Claude Code uses a hybrid — CLAUDE.md up front plus glob/grep just in time, bypassing "stale indexing" — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Building effective agents" (Dec 19 2024, with a 2026 note pointing to newer managed-agents docs): "For many applications, optimizing single LLM calls with retrieval and in-context examples is usually enough"; "add complexity only when it demonstrably improves outcomes"; the most successful implementations used "simple, composable patterns", not complex frameworks — [Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
- For coding specifically, the same post argues agents work because "code solutions are verifiable through automated tests" and agents can iterate on test feedback, but "human review remains crucial" — [Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
- Long-context degradation is multi-causal: position (Liu et al.), semantic ambiguity and distractors (Chroma), need for latent/world knowledge (NoLiMa: 72.4% of its needle–question pairs require external knowledge), and inability to detect absence (AbsenceBench) — [arXiv:2307.03172](https://arxiv.org/abs/2307.03172); [Chroma Research](https://research.trychroma.com/context-rot)
- Chroma explicitly lists a key open limitation: disentangling how much degradation comes from intrinsic task difficulty versus input length, and does not explain the mechanism ("beyond the scope of this report") — [Chroma Research](https://research.trychroma.com/context-rot)
- Long-horizon context management has three distinct primitives: **compaction** (whole-transcript summary, lossy by design, ~25-line minimal implementation described), **tool-result clearing** (sub-transcript: replaces old `tool_result` payloads with placeholders while keeping the `tool_use` record; "one of the safest, lightest-touch" options), and **memory** (structured notes persisted outside the window, pulled back later). "Start with the one that matches the bottleneck you're actually observing" — [Claude Cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)
- Choosing among long-horizon techniques: compaction maintains conversational flow; note-taking excels for iterative development with clear milestones; multi-agent architectures suit parallel exploration; subagents return only condensed summaries (often 1,000–2,000 tokens) while exploration stays isolated — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Waiting for larger context windows might seem like an obvious tactic. But it's likely that for the foreseeable future, context windows of all sizes will be subject to context pollution and information relevance concerns" — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Inferences

- The evidence explains *why* the ETH paper found repository overviews useless: an overview is a distractor-rich, low-signal block that competes for an attention budget already stretched by code and tool output.
- Context engineering reframes memory as one primitive among several for the same finite-resource problem, not a fundamentally different capability. Memory is the cross-session leg of context management.
- "Smallest set of high-signal tokens" is a design principle, not a measured threshold; no paper found provides a universal optimal context size for coding agents.
- The field's trajectory is toward less human curation as models improve, but "do the simplest thing that works" remains the recommended default.

### Gaps

- Primary in-context-learning papers (e.g. Brown et al. 2020 and follow-ups on example selection/ordering) were not fetched; ICL claims here come from Anthropic's synthesis, not original experiments.
- No study found measuring an instruction-file size/adherence curve in coding agents (ETH varied content type, not length).
- No benchmark found testing long-context degradation specifically for coding-agent instruction context (as opposed to QA retrieval).

## Q4: When do practitioners say a memory system becomes necessary rather than just more instructions?

### Takeaway

Vendors treat the two as complementary with a clear division of labour: instruction files hold stable, human-written, version-controlled rules; memory holds evolving, agent-written learnings and cross-session state that cannot be derived from code. Memory becomes necessary at the boundary of time (context resets), provenance (agent-generated knowledge), and non-derivability (history, preferences, decisions).

### Cited Findings

- Claude Code ships both mechanisms and defines the split: **CLAUDE.md** = "instructions and rules", written by you, project/user/org scope, loaded every session; **auto memory** = "learnings and patterns", written by Claude, per repository shared across worktrees, loaded every session via the first 200 lines/25 KB of `MEMORY.md`. "Both are loaded at the start of every conversation. Claude treats them as context, not enforced configuration" — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Auto memory has four typed categories: `user` (role, expertise, preferences), `feedback` (corrections and confirmed approaches), `project` (ongoing work, deadlines, decisions "that Claude can't derive from the code or git history"), `reference` (where to find external information). It "skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes" and "skips anything your CLAUDE.md files already say" — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Trigger heuristic for adding to CLAUDE.md: "Claude makes the same mistake a second time"; a review catches something it should have known; "You type the same correction or clarification into chat that you typed last session"; a new teammate would need the same context. Multi-step procedures go to a skill or path-scoped rule instead — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Auto memory is machine-local, not shared across machines or cloud environments; memory files are exempt from transcript cleanup; topic files are read on demand rather than at startup — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- **Long-running agent harness (Anthropic Research, Nov 26 2025):** "each new session begins with no memory of what came before"; compaction alone is insufficient. The fix is an initializer agent that writes `init.sh`, `claude-progress.txt`, an initial git commit and a structured JSON feature list (200+ features in the claude.ai clone example, all initially marked failing), and a coding agent that works one feature at a time, reads git logs + progress file + feature list at session start, and ends with a commit and progress update — [Anthropic Research](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- That report's framing: "getting agents to make consistent progress across multiple context windows remains an open problem"; the progress file and git history are "the key insight" for rapid catch-up with a fresh window — [Anthropic Research](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- **Structured note-taking / agentic memory** (Anthropic, Sep 29 2025): the agent writes notes to storage outside the context window and reads them after resets, enabling "persistent memory with minimal overhead"; the Pokémon agent tracks tallies across thousands of steps (e.g. "for the last 1,234 steps I've been training my Pokémon in Route 1") and develops maps and strategies without prompt structure, which "enables long-horizon strategies that would be impossible when keeping all the information in the LLM's context window alone" — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Cookbook distinction (Mar 20 2026):** compaction handles in-session conversation growth; clearing handles bulky re-fetchable tool results; "memory moves information out of the window so it survives across sessions" — [Claude Cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)
- **MemGPT** (Packer et al., arXiv:2310.08560, v1 Oct 12 2023, v2 Feb 12 2024): "virtual context management" inspired by OS hierarchical memory, moving data between fast/slow tiers and using interrupts for user/agent control flow; evaluated on document analysis far exceeding the context window and on multi-session chat where agents "remember, reflect, and evolve dynamically" — [arXiv:2310.08560](https://arxiv.org/abs/2310.08560)
- Enforcement boundary: "To block an action regardless of what Claude decides to do, use a PreToolUse hook"; managed CLAUDE.md is for guidance while managed settings (`permissions.deny`, sandbox) are for technical enforcement — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Practitioner counterpoint: a single-task benchmark "cannot capture the compound value of AGENTS.md in multi-session, multi-agent workflows where consistency matters more than any individual task's success rate", and enterprise monorepos have a much wider information gap than well-documented OSS repos — opinion from a Codex book author — [Vaughan](https://codex.danielvaughan.com/2026/04/13/what-eth-zurich-paper-gets-wrong-right-about-agents-md/)
- Practitioner friction: existing setups work better inside a team than between strangers; copying configs causes low awareness of what is in the context and accidental duplication/contradiction; "you have to use a configuration for a while to be able to say if it's working well or not" — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html)

### Inferences

- The vendor architecture is itself the strongest evidence that this is not an either/or: both instruction files and memory are shipped, with different authors, scopes, lifetimes, and loading rules.
- The operative boundary conditions appear to be: (1) **time** — across sessions/context resets; (2) **provenance** — human-curated rules versus agent-learned notes; (3) **derivability** — if code/git already contains it, neither mechanism should hold it; (4) **scope** — version-controlled team sharing versus machine-local; (5) **enforcement** — context versus hooks/settings.
- Memory is necessary for facts that cannot be expressed as short, stable, always-true rules: a decision made on a specific date, a user preference inferred from corrections, the state of a half-finished feature, a progress log.
- Large codebases matter less as a trigger for memory than does *time and state*: a big repo is handled by just-in-time retrieval; many sessions with accumulating state is what demands memory.

### Gaps

- No controlled A/B study comparing "more/better instructions" against "a memory system" on the same tasks.
- No data on how many sessions or how large a codebase must be before memory pays off.
- Little evidence on personal preferences specifically, despite auto memory having `user` and `feedback` types designed for them.
- No measured accuracy/precision data for what agents choose to save to auto memory, or for false/outdated memories.

## Q5: Is reasoning about "when to use memory vs instructions" mostly settled, or is it an open/contested question?

### Takeaway

The taxonomy is largely settled in practice — vendors agree on which mechanism does which job and ship them together — but the empirical question is open and publicly contested. Two 2026 studies disagree on headline outcomes, both are narrow, and the strongest public claims are opinion rather than measurement.

### Cited Findings

- The ETH authors' own conclusion is conditional and explicitly unsettled: context files are "useful for specifying non-standard coding practices", but "any attempts to improve performance should be rigorously evaluated before deployment" — [arXiv:2602.11988](https://arxiv.org/abs/2602.11988)
- Lulla et al. call their work "a first step" and "initial empirical evidence", list agent stochasticity, single framework/model, task-size constraints and absence of correctness evaluation as limitations, and set out a research roadmap — [arXiv:2601.20404](https://arxiv.org/abs/2601.20404)
- Anthropic: "getting agents to make consistent progress across multiple context windows remains an open problem", and "it's still unclear whether a single, general-purpose coding agent performs best across contexts, or if better performance can be achieved through a multi-agent architecture" — [Anthropic Research](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- Fowler (Feb 5 2026): the field is "in a 'storming' phase right now and will surely converge on a simpler set of features"; "in spite of the name, ultimately this is not really engineering" because execution depends on LLM interpretation and "we can never be certain of anything" — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html)
- Direct conflict in measured findings: Lulla et al. report faster and cheaper runs with AGENTS.md; the ETH abstract reports "does not generally improve task success rates, while increasing inference cost by over 20%". Secondary ETH summaries also conflict with the current v3 abstract on human-written files (+4% versus "does not generally improve ... for both LLM-generated and developer-committed context files") — [arXiv:2601.20404](https://arxiv.org/abs/2601.20404); [arXiv:2602.11988](https://arxiv.org/abs/2602.11988); [DAIR.AI](https://academy.dair.ai/blog/agents-md-evaluation)
- Public pushback argues the ETH study tested redundant files on well-documented repositories, measured a single task rather than multi-session consistency, and conflated poor-quality context with context itself; its recommendation is "write less, write better, and verify what your agent actually reads". This is an opinion piece by the author of a Codex CLI book, not a competing experiment — [Vaughan](https://codex.danielvaughan.com/2026/04/13/what-eth-zurich-paper-gets-wrong-right-about-agents-md/)
- Trade press framed the ETH result as "AGENTS.md files may often hinder AI coding agents" and recommended omitting LLM-generated files — [InfoQ](https://www.infoq.com/news/2026/03/agents-context-file-value-review/) (title/snippet from search results; page not fetched, so treat as secondary)
- Convergence despite the debate: vendors consistently ship layered loading — always-on CLAUDE.md, path-scoped rules, on-demand skills, subagents, hooks, plus two memory systems — as the practical "answer" to where information should live — [Claude Code memory docs](https://code.claude.com/docs/en/memory); [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html); [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Inferences

- Best framing for the final report: **settled as a design pattern, open as an empirical question.** Practitioners broadly agree on the division of labour; evidence for the value of any specific configuration is weak, version-dependent, and measured under different frames.
- The live contest is about the measurement frame: single-task success versus multi-session consistency, cost and risk; well-documented OSS versus proprietary monorepos; human-written versus generated files; efficiency versus correctness.
- "Context engineering" has absorbed the question: memory, compaction, clearing, rules, skills and subagents are now discussed as interchangeable levers on one finite attention budget, which reduces the old binary but does not resolve which lever wins for which workload.

### Gaps

- No meta-analysis or systematic review of context-file effectiveness found.
- No direct memory-versus-instructions experiment found.
- Could not verify widely repeated adoption statistics (e.g. 35–55% fewer bugs; "60,000+ repositories" is verifiable from agents.md, the bug statistic is not) from primary sources.
- No source found that directly adjudicates the multi-session/enterprise-monorepo claim with measurements rather than argument.
