# Practitioner and vendor evidence: persistent memory in coding agents vs instruction/rules files

Research date: 2026-11-19. Method note: the `websearch` tool failed for every query with HTTP 402, so all findings below come from direct `webfetch` of primary vendor docs, the Hacker News Algolia API (`hn.algolia.com/api/v1/search`, used as the practitioner-discussion corpus), and vendor/practitioner blogs. This means coverage is strong for documented features and HN discourse, and weaker for Reddit, conference talks, and survey reports (see Gaps). The fetched docs describe a 2026 product state (e.g. Gemini CLI was replaced by Antigravity CLI on 2026-06-18 for unpaid/Google One users; Claude Code v2.1.2xx; Cursor shipping Claude 4.7–5.x and GPT-5.6-era models) — treat version-specific details as environment-current, not timeless.

Evidence labels used below: **[measured]** = a published benchmark, controlled comparison, or traced dataset; **[vendor claim]** = first-party assertion, possibly with self-run numbers; **[anecdote]** = individual practitioner report; **[docs]** = documented feature behavior, not an outcome claim.

## 1. What memory features the major coding agents offer as of 2026, and what the docs say memory is for

### Takeaway
The industry has converged on a two-tier model: a committed instruction file (CLAUDE.md / AGENTS.md / .cursor/rules / GEMINI.md / .clinerules / aider conventions) that a human writes, plus an optional *agent-written* auto-memory that accumulates notes. Vendors are explicit that neither is enforced configuration — both are "context," and reliability degrades with length and conflict.

### Cited Findings

- **Claude Code** documents two complementary memory systems loaded at the start of every session. Table verbatim: "CLAUDE.md files — Who writes it: You; What it contains: Instructions and rules; Scope: Project, user, or org; Loaded into: Every session; Use for: Coding standards, workflows, project architecture." vs "Auto memory — Who writes it: Claude; What it contains: Learnings and patterns; Scope: Per repository, shared across worktrees; Loaded into: Every session (first 200 lines or 25KB); Use for: Your preferences, corrections you give Claude, project context Claude can't derive from the code." — [Anthropic, "How Claude remembers your project"](https://code.claude.com/docs/en/memory) **[docs]**
- Same doc: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides to do, use a PreToolUse hook instead. The more specific and concise your instructions, the more consistently Claude follows them." It also states "Target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." — [Anthropic memory doc](https://code.claude.com/docs/en/memory) **[docs]**
- Auto memory specifics: four note types (`user`, `feedback`, `project`, `reference`); stored at `~/.claude/projects/<project>/memory/` with a `MEMORY.md` index; only the first 200 lines or 25 KB of `MEMORY.md` load at session start, topic files load on demand; "Claude skips anything it can derive from the codebase... It also skips anything your CLAUDE.md files already say"; machine-local, not shared across machines; on by default in local sessions, off by default in self-hosted environments. Subagents can maintain separate auto memory. — [Anthropic memory doc](https://code.claude.com/docs/en/memory) **[docs]**
- Claude Code reads `AGENTS.md` directly as project instructions (v2.1.277+), with a configurable "Project instructions" setting (`claude-md-or-agents-md` default, `claude-md-and-agents-md`, `claude-md`, `managed-only`); `/init` migrates Cursor, Copilot, Windsurf and Cline rule files into CLAUDE.md. A `/doctor prompt-audit` command (v2.1.283+) checks for outdated/conflicting instruction files. — [Anthropic memory doc](https://code.claude.com/docs/en/memory) **[docs]**
- **Cursor** has rules, not an autonomous memory store, and says so: "Large language models don't retain memory between completions. Rules provide persistent, reusable context at the prompt level. When applied, rule contents are included at the start of the model context." Four rule types: Project (`.cursor/rules/*.mdc`, version-controlled), User (global), Team (dashboard-managed, enforceable on Team/Enterprise), and `AGENTS.md` (plain-markdown alternative, including nested subdirectories). Modes: `Always Apply`, `Apply Intelligently` (by description), `Apply to Specific Files` (globs), `Apply Manually` (@-mention). — [Cursor, "Rules"](https://cursor.com/docs/context/rules) **[docs]** (Note: fetching `cursor.com/docs/context/memories` returned the same Rules page — no separate Cursor memory doc was reachable.)
- Cursor best practice is explicitly anti-staleness: "Start simple. Add rules only when you notice Agent making the same mistake repeatedly. Don't over-optimize before you understand your patterns," and "Reference files instead of copying their contents. This keeps rules short and prevents them from becoming stale as code changes." Team rules apply in precedence order "Team Rules → Project Rules → User Rules"; "AI guidance should not be your only security control." — [Cursor Rules](https://cursor.com/docs/context/rules) **[docs]**
- **Cline "Memory Bank"** is a *methodology*, not a built-in feature: a set of six markdown files (`projectbrief.md`, `productContext.md`, `activeContext.md`, `systemPatterns.md`, `techContext.md`, `progress.md`) plus custom instructions pasted into `.clinerules/memory-bank.md`. The prescribed prompt states: "I am Cline... my memory resets completely between sessions. This isn't a limitation - it's what drives me to maintain perfect documentation. After each reset, I rely ENTIRELY on my Memory Bank... I MUST read ALL memory bank files at the start of EVERY task - this is not optional." Cline docs note it "works with any AI that can read docs" and pairs it with `/newtask` and `/smol` for context-window management. — [Cline, "Memory Bank"](https://docs.cline.bot/prompting/cline-memory-bank) **[docs]**
- **Aider** offers no memory subsystem; persistence is via a conventions markdown file added read-only to the chat (`/read CONVENTIONS.md` or `read: CONVENTIONS.md` in `.aider.conf.yml`), plus a repository map for code context and community conventions files. Its docs demonstrate that including `CONVENTIONS.md` changed output (httpx + type hints) versus omitting it (requests, no types) — a small, illustrative A/B, not a benchmark. — [Aider, "Specifying coding conventions"](https://aider.chat/docs/usage/conventions.html) **[docs / anecdotal illustration]**
- **Gemini CLI** documents both "Manage context and memory" and a dedicated "Auto Memory" feature (marked experimental 🔬), plus `GEMINI.md` project context and a "Memory import processor" reference for consuming memory from various sources. Note the doc states Gemini CLI was replaced by Antigravity CLI on 2026-06-18 for unpaid tier/Google One users and was not optimized for Gemini 4 Argon. — [Gemini CLI docs](https://geminicli.com/docs/) **[docs]**
- **GitHub Copilot** is covered as a rules/instructions-based system in practitioner comparisons: `.github/copilot-instructions.md` and (per Claude Code's migration list) Copilot rules; a dedicated practitioner writeup exists on "GitHub Copilot Memory and Dreaming: where memories live." — [Anthropic memory doc](https://code.claude.com/docs/en/memory); [Harbor blog index](https://gethrbr.com/blog/do-agents-need-memory) **[docs / secondary]**
- **OpenAI Codex / Codex CLI** uses `AGENTS.md` as its instruction file; practitioner reports describe its per-project memory and note that it "ignores" AGENTS.md under some conditions. — [Harbor blog index](https://gethrbr.com/blog/do-agents-need-memory); [HN comment on Codex logging bug thread](https://news.ycombinator.com/item?id=48626930) **[anecdote / secondary]**
- **Windsurf** is represented in the ecosystem as `.windsurf/rules` / `.windsurfrules` files, which Claude Code's `/init` can import. No dedicated Windsurf memory feature was found in this research. — [Anthropic memory doc](https://code.claude.com/docs/en/memory) **[docs]**
- **AGENTS.md** has become the cross-vendor interchange format: Claude Code reads it natively or via `@AGENTS.md` import/symlink; Cursor supports root and nested AGENTS.md; Claude Code's `/import` carries it into CLAUDE.md alongside MCP servers, commands, subagents and skills. — [Anthropic memory doc](https://code.claude.com/docs/en/memory); [Cursor Rules](https://cursor.com/docs/context/rules) **[docs]**

### Inferences
- The "memory vs instructions" framing is partly a false dichotomy at the feature level: every major vendor's *persistent* mechanism is a text file injected into context, and the only genuine architectural difference is *who writes it and how it is selected* (human-committed file vs agent-written note recalled by similarity).
- All vendors converge on the same failure mode in their own docs: length, staleness, and conflicting rules degrade adherence. Recommendation to keep files short and scope rules to paths is universal.
- Enforcement is deliberately outside the memory layer: hooks, managed settings, and guardrails are the recommended mechanism for hard rules (explicitly stated by both Anthropic and Cursor).
- Cline's Memory Bank is effectively a manually maintained AGENTS.md-style document set with a stronger reading ritual; it is not evidence that automatic memory works.

### Gaps
- Could not retrieve dedicated first-party docs for GitHub Copilot "Memory/Dreaming", Codex "memories", Cursor "memories", or Windsurf memory; those are known only through a vendor blog's article index and HN discussion. Direct verification is needed.
- No published per-vendor usage statistic (what fraction of teams enable auto memory, or how many memories a typical repo accumulates) was found.

## 2. What vendors claim the benefit is, and whether it is backed by measurements

### Takeaway
Vendor claims are overwhelmingly qualitative ("persistent partner," "learn from corrections," "no more re-explaining"). The few numbers that exist are self-run benchmark results from third-party memory products, not from the coding-agent vendors, and there is no vendor-published controlled trial showing auto memory improves coding-task success.

### Cited Findings

- **Claude Code claim:** "Auto memory lets Claude accumulate knowledge across sessions without you writing anything," and "Auto memory lets Claude learn from your corrections without manual effort." No success-rate, token, or time measurement is attached on the docs page. — [Anthropic memory doc](https://code.claude.com/docs/en/memory) **[vendor claim, unmeasured]**
- **Cursor claim:** rules "give the AI consistent guidance for generating code, interpreting edits, or helping with workflows"; "Team Rules... provide a powerful way to ensure consistent coding standards, practices, and workflows across your entire team without requiring individual setup." No measurement. — [Cursor Rules](https://cursor.com/docs/context/rules) **[vendor claim, unmeasured]**
- **Cline claim:** Memory Bank "transforms Cline from a stateless assistant into a persistent development partner." No measurement; framed as a documentation methodology. — [Cline Memory Bank](https://docs.cline.bot/prompting/cline-memory-bank) **[vendor claim, unmeasured]**
- **Aider** provides the only vendor-side illustration resembling a comparison: same task with vs without `CONVENTIONS.md`, showing the conventions file changed library/type-hint choices. It is a single worked example, explicitly not quantified. — [Aider conventions](https://aider.chat/docs/usage/conventions.html) **[illustration, not measured]**
- **Third-party memory vendor Engram** publishes numbers: 80.0% on LOCOMO vs Mem0 66.9% and a "MEMORY.md baseline" of 28.8%; "776 tokens/query" vs "~2,000+" for Mem0; "93.6% fewer tokens than full context" (1,504 vs 23,423 tokens/query); 2,500 npm installs in first five days. Its thesis: "Recall-based beats extraction-based. Engram invests intelligence at read time, when you know the query, not write time when you don't know what'll matter." — [Engram benchmark/compare](https://www.engram.fyi/compare); [HN Show HN post](https://news.ycombinator.com/item?id=47203853) **[vendor claim; self-run; third-party benchmark (LOCOMO) is conversational memory, not coding-task success]**
- **Practitioner-vendor Harbor** (a competing "shared memory" product) aggregates five 2026 papers as the strongest available measured evidence (see §4), but its page is itself marketing for Harbor and the papers were read from abstracts, not verified in full here. — [Harbor, "Do coding agents need memory or documentation?"](https://gethrbr.com/blog/do-agents-need-memory) **[vendor-curated synthesis of measured claims]**
- A Hacker News practitioner building a memory layer explicitly flags the measurement problem: evaluating memory is "harder than checking whether the agent solved the next task with fewer tokens," because the agent may web-search or rediscover the answer, "so the benchmark is not just measuring success. It is also measuring provenance." He also notes timeline leakage (the repo already contains the "memory" answer) and the "easy bad strategy" of writing a very detailed summary after every task. — [HN "Coding Agent Memory Benchmarks"](https://news.ycombinator.com/item?id=48475850) **[anecdote about methodology, 2 points, 0 comments]**

### Inferences
- The burden of proof is asymmetric: the vendors with the widest deployment (Anthropic, Cursor, Google, Cline) make no outcome claims at all; the vendors with numbers are small third-party memory products marketing against Mem0/Zep/Letta.
- Even the positive numbers measure conversational recall (LOCOMO), not "did the agent ship a better patch." Engram's own comparison includes a MEMORY.md baseline of only 28.8%, which is a data point *against* flat instruction/memory files but says nothing about a curated AGENTS.md.
- No vendor published evidence that their memory feature beats their own instruction-file mechanism on task success, tokens, or time. That is the central evidentiary hole.

### Gaps
- No Stack Overflow Developer Survey, GitHub Octoverse, or other large developer-survey data on adoption or perceived value of coding-agent memory was retrievable in this session.
- No vendor-controlled A/B (memory on vs off) on SWE-bench-style coding tasks was found from a coding-agent vendor.
- The arXiv papers cited by Harbor were not fetched directly; their existence and exact numbers are reported second-hand.

## 3. Practitioner reports: did memory help or hurt? Stale context, wasted tokens, degraded performance

### Takeaway
Practitioner sentiment is sharply split by *kind* of persistence: hand-maintained, scoped instruction files are broadly defended; similarity-retrieved agent memory is widely reported as unreliable, stale, unauditable, and sometimes actively harmful. The strongest single critique reached the HN front page.

### Cited Findings

- **Kevin Liao, "Agents don't need memory, they need documentation"** reached the HN front page on 2026-10-03 with 369 points and 281 comments by 10-05. His case, as summarized: memory plugins "retrieve snippets by similarity, without context, with stale facts treated as current, and nobody can audit them"; a folder of markdown the agent reads before work and updates after is better. — [Liao blog](https://liao.gg/blog/agents-dont-need-memory); [HN thread](https://news.ycombinator.com/item?id=49945933) **[practitioner argument; high-engagement]**
- The thread "pushed back from both sides." A recurring counter-objection: a markdown folder has the same unknown-unknowns problem, since the agent still has to guess which page matters, and "whatever is written needs enforcing, because a rule such as using jq rather than an ad-hoc Python script to parse JSON gets broken anyway." — [Harbor synthesis of the HN thread](https://gethrbr.com/blog/do-agents-need-memory) **[secondary report of anecdote]**
- **Concrete harm anecdote — silent truncation:** "MEMORY.md is automatic but it only gets read once at session startup, it's scoped per repo so your cross-project preferences don't carry over, and once it gets long enough only the top N lines are read. Older notes just silently disappear from context regardless of how important they are. I had a note about a critical config value fall off the bottom and cost me an hour." Author then built a hook-based memory system (cmr-memory) that injects only relevant notes before each tool call. — [HN comment by NBenkovich](https://news.ycombinator.com/item?id=47593178) **[anecdote]**
- **Context-bloat workarounds are common.** One practitioner: "every turn it goes to the top of the stack and it is the very last thing they see... And then it gets taken out of the conversation so that it doesn't get sent to the agent the next turn (no context bloat). It has restored so much sanity." Another deliberately avoids `@` imports in CLAUDE.md and uses plain path references "without using the '@' symbol which to my understanding always causes CLAUDE to ingest the linked files resulting in unnecessarily bloating your prompt context." — [HN comment on "I'm becoming AI-blind"](https://news.ycombinator.com/item?id=49386699); [HN comment on Claude Skills](https://news.ycombinator.com/item?id=45619537) **[anecdote]**
- **Symlink double-loading:** a practitioner switched from symlinking AGENTS.md to CLAUDE.md after experimenting and finding that the agent could read AGENTS.md directly in a file listing and load it twice, "essentially double the token impact / context bloat." — [HN comment](https://news.ycombinator.com/item?id=48626930) **[anecdote; note current Claude Code docs say a symlink is read once, so this may be version-dependent]**
- **Bloat vs. value distinction:** "My takeaway from these CLAUDE.md/AGENTS.md efforts isn't that agents can't maintain any form of context at all, rather, that bloated CLAUDE.md files filled with data that agents can gather on the spot very quickly are counter-productive. For information which cannot be gathered on the spot quickly, clearly (to me) context helps improve quality." The same commenter cites an arXiv study (2602.11988) finding cheaper-LLM auto-generated AGENTS.md performed worse than human-edited AGENTS.md. — [HN comment](https://news.ycombinator.com/item?id=47899844) **[anecdote + secondary citation]**
- **Directory-scoped instruction files are the popular alternative to memory:** "put [documentation] in 'src/persistence/CLAUDE.md' instead of the main one. Claude pulls in those files automatically whenever it tries to read a file in that directory. I find that to be a very effective technique... but still keep them focused and avoid context bloat." — [HN comment on "Writing a good Claude.md"](https://www.humanlayer.dev/blog/writing-a-good-claude-md), [thread](https://news.ycombinator.com/item?id=46098838) **[anecdote]**
- **Staleness in shared memory is reported as a team-level failure mode:** "For one developer this is an annoyance. For a team it compounds: one session's mistaken note becomes every session's premise, and the correction sits next to it, losing." — [Harbor blog](https://gethrbr.com/blog/do-agents-need-memory) **[vendor-authored synthesis of measured papers]**
- **Memory-product builders themselves acknowledge limits:** ClawMem's author: "the system is only as good as what you index. A vault with three memory files gives deservedly thin results"; Engram's HN post notes "CLAUDE.md helps but it's manual and doesn't scale." — [HN ClawMem](https://news.ycombinator.com/item?id=47472965); [HN Engram](https://news.ycombinator.com/item?id=47203853) **[vendor/author admission + claim]**
- **A skeptical view of RAG-style retrieval from a Claude Code user:** after discovering scripts + CLAUDE.md worked, "MCP seemed like context bloat when a `tools/my-script -h` would put it in context on request," and reading RAG was "what? That's it? A 'prelude function' to dump 'probably related' things into the context?" — [HN comment on "The RAG Obituary"](https://news.ycombinator.com/item?id=45439997) **[anecdote]**
- Memory tooling is crowded with small, low-engagement Show HN launches (Skillsync, Hive Memory, thr, ClawMem, Engram, Codela, Recall, AgentOS, cAGENTS), most with 0–6 points and 0–1 comments — evidence of high builder interest but little independent validation. — [HN Algolia search results](https://hn.algolia.com/api/v1/search?query=coding%20agent%20memory&tags=story) **[observation]**

### Inferences
- The dominant practitioner pattern is not "memory vs no memory" but "small, human-owned, path-scoped context vs large, agent-owned, similarity-retrieved context." Most complaints (bloat, silent truncation, double-loading, staleness) are consequences of *how much* text is injected and *who validates it*, not of persistence per se.
- Reports of harm are mostly anecdotal and version-dependent; the strongest structured evidence comes from the 2026 papers in §4, not from individual blogs.
- There is a notable asymmetry: builders of memory products frame CLAUDE.md as "manual, doesn't scale"; users of those products frequently report that a well-scoped CLAUDE.md is sufficient and that retrieval adds noise.

### Gaps
- Reddit, Discord, conference talks, and developer surveys were not searched (websearch unavailable). These may contain the largest body of practitioner sentiment.
- No longitudinal study of a team using memory for months versus a team using only instruction files was found.
- Little quantified practitioner data on tokens or latency cost of memory hooks in real sessions; only one self-reported benchmark (Engram) and one anecdotal "cost me an hour."

## 4. Is there any direct comparison of outcomes (task success, token use, time) between memory systems and instruction-file-only teams?

### Takeaway
Yes — but only from a small set of 2026 arXiv papers (read via a vendor's abstract-level synthesis), and they point to a nuanced conclusion: *past experience helps when injected directly; the memory systems that decide what to store and recall mostly destroy that benefit.* No team-level A/B of memory vs committed instruction files was found.

### Cited Findings

- **VibeMemBench (arXiv:2609.23570, 2026-09-20), as reported:** 111 coding targets built from 90 real repositories, each paired with past experience *verified to help*. Directly injecting that experience "raised the task resolution of four of five held-out solvers by 1.1 to 4.5 points and cut steps for all five." When four existing memory systems had to build and retrieve the experience from the same history themselves, "eleven of twelve solver and system pairings failed to beat the same agent with memory off." — [Harbor blog citing arXiv:2609.23570](https://gethrbr.com/blog/do-agents-need-memory) **[measured, per abstract; secondary]**
- **Shared-memory false-belief paper (arXiv:2609.30813, 2026-09-25), as reported:** once an uncontested false belief entered a shared store, the answering agent asserted it in 97–99% of probes across four agent families. Admission policy mattered: gating on declared source type held false adoption to 6–9% versus 22–47% for other answering policies. Deduplicating sources "rejected true claims along with the false ones." — [Harbor blog citing arXiv:2609.30813](https://gethrbr.com/blog/do-agents-need-memory) **[measured, per abstract; secondary]**
- **"Revoked but Still Authoritative" (arXiv:2609.08258, 2026-09-08), as reported:** five agent-memory systems were loaded with a revoked policy and its replacement; "None enforced the revocation by default. The revoked fact came back wherever the retrieval layer could see it, outranked its replacement, and led agents to the unsafe action." — [Harbor blog citing arXiv:2609.08258](https://gethrbr.com/blog/do-agents-need-memory) **[measured, per abstract; secondary]**
- **Documentation-use trace (arXiv:2608.20195, 2026-08-20), as reported:** 557 agentic sessions and 33,097 agent PRs traced. Instruction files and working notes made up 60.5% of agents' documentation interactions vs 10.6% for classical technical docs and 1.3% for API references. "The link from reading to editing was unresolved: the probability that a consultation was followed directly by an edit was 0.002, and only a stage-adjusted model put the association above chance." Docs trail code: in multi-commit PRs changing both, code was touched first 4.7x more often. — [Harbor blog citing arXiv:2608.20195](https://gethrbr.com/blog/do-agents-need-memory) **[measured, per abstract; secondary]**
- **"When 'Do Not' Is Not Deny" (arXiv:2608.23550, 2026-08-24), as reported:** security rules from 481 public CLAUDE.md files were checked for a built-in Claude Code control enforcing them; only ~4–16% had one (4.4% under the strictest standard). The author calls CLAUDE.md "a write-only channel: you write a rule and never learn whether anything enforces it." — [Harbor blog citing arXiv:2608.23550](https://gethrbr.com/blog/do-agents-need-memory) **[measured, per abstract; secondary]**
- **Harbor's synthesis** translates these into five required properties: a gate on what gets in; retirement enforced on read; delivery with the task; hard rules as controls, not prose; and a count of what was used ("eleven of twelve pairings failed to beat memory off. Without a count per item, you cannot see which items earn their place"). — [Harbor blog](https://gethrbr.com/blog/do-agents-need-memory) **[vendor framework built on measured claims]**
- HN commenter cites arXiv:2602.11988 as "the one (1) study that showed that when cheaper LLM's auto-generated an AGENTS.md, it performed more poorly than human editted AGENTS.md" — relevant to auto-generated memory vs human-written instructions, but not verified directly here. — [HN comment](https://news.ycombinator.com/item?id=47899844) **[secondary]**

### Inferences
- The most defensible empirical conclusion available: *experience injection works; autonomous memory selection mostly does not.* Direct injection of verified past experience improved 4/5 solvers; 11/12 pairings with existing memory systems failed to beat no memory.
- Staleness is not hypothetical: revoked facts outrank replacements by default in five systems, and uncontested false claims persist in 97–99% of probes. This is the strongest measured case against ungated shared memory.
- Instruction files have their own measured weakness: they are read heavily (60.5% of documentation interactions) but the read→edit link is near chance (p=0.002), and only 4–16% of written security rules map to an enforcing control. So "just use AGENTS.md" is not a complete answer either.
- No study compared *teams* using memory versus teams using only committed instruction files on task success / token spend / time. All comparisons are agent/solver-level on synthetic or reconstructed tasks.

### Gaps
- The five arXiv papers were not opened directly. Numbers should be verified against the primary PDFs before inclusion in a final report.
- No team-level, real-repository, longitudinal comparison found; no data on wall-clock time or cost saved.
- No benchmark that measures "provenance" (whether the memory actually caused the success) was found implemented — only the HN practitioner's description of the problem.

## 5. How third-party memory systems position themselves, and what evidence they provide

### Takeaway
Third-party systems position themselves as the missing layer that instruction files cannot provide: cross-session, cross-project, automatically captured, semantically retrieved memory. Evidence is mostly self-run benchmarks on generic conversational-memory datasets, install counts, and architecture narratives — not independent coding-task evaluations.

### Cited Findings

- **Engram** (MCP server for Claude Code/Cursor): "every Claude Code or Cursor session starts from zero. You re-explain your architecture, conventions, past decisions. CLAUDE.md helps but it's manual and doesn't scale." Three memory tiers (explicit, implicit behavioral patterns, synthesized meta-observations). Claims 80% LOCOMO (19.6% relative improvement over Mem0), 776 tokens/query, 93.6% fewer tokens than full context, 2,500 npm installs in five days; comparison table vs Mem0, Zep/Graphiti, Letta/MemGPT. — [Engram compare](https://www.engram.fyi/compare); [HN Show HN](https://news.ycombinator.com/item?id=47203853) **[vendor claim]**
- **ClawMem**: "open-source context engine that gives AI coding agents persistent memory across sessions," shared SQLite vault between Claude Code and OpenClaw; retrieval "Frankenstein" assembled from QMD, SAME, MAGMA, A-MEM, Engram; uses BM25 + vector + RRF + query expansion + cross-encoder reranking, optional 12 GB-VRAM local SOTA embed/rerank stack. Author is explicit it is "a polished WIP, not a finished product" and "the system is only as good as what you index." — [HN Show HN](https://news.ycombinator.com/item?id=47472965) **[vendor claim + self-caveat]**
- **Beads** (Steve Yegge): "A coding agent memory system" — positioned as an external memory layer for coding agents; HN submissions 19, 4, 2, 1 points with 0–1 comments each, i.e. notable but little discussion. — [Beads article](https://steve-yegge.medium.com/introducing-beads-a-coding-agent-memory-system-637d7d92514a); [HN search](https://hn.algolia.com/api/v1/search?query=coding%20agent%20memory&tags=story) **[vendor claim; low engagement]**
- **cmr-memory** (HN): built because "CLAUDE.md is manual — you maintain it. MEMORY.md is automatic but it only gets read once at session startup... older notes just silently disappear from context." Uses a small LLM as a relevance filter before each tool call with a `--when` activation condition, chunking + Haiku + prompt caching, and PreToolUse/PostToolUse hooks; dedup step exists specifically so re-injection "just bloats context for no reason." — [HN comment](https://news.ycombinator.com/item?id=47593178) **[vendor claim + anecdote; no benchmark]**
- **Hive Memory**: MCP server for cross-project memory — "tools like Claude Code and Codex have per-project memory, but when you switch between projects, the agent starts from scratch." 14 MCP tools, local JSON/Markdown in `~/.cortex/`. — [HN Show HN](https://news.ycombinator.com/item?id=47207442) **[vendor claim]**
- **thr**: local semantic memory CLI — "I got tired of telling my coding agent the same things over and over. I also didn't want to use a hosted memory service like supermemory, or run a local server like mem0." Local embeddings with a minimum distance threshold to avoid weak matches. — [HN Show HN](https://news.ycombinator.com/item?id=47999377) **[vendor claim]**
- **Codela**: "production memory" — checks deploys against production behavior and "teaches your agents so they don't repeat the mistake," motivated by the fact that what an agent did wrong "never reaches the agent, so futures session usually make the same mistake." — [HN Show HN](https://news.ycombinator.com/item?id=50428670) **[vendor claim]**
- **Harbor / gethrbr**: positions itself against both memory and docs — "Neither, as they are usually built." Product reads team decisions from Slack/PRs/docs, requires human approval, dates facts, enforces retirement, injects rules at session start via hooks, converts hard rules to guardrails, and reports "served" vs "cited" counts. ### Inferences
- The category's shared narrative is "instruction files are manual, per-project, and don't scale; memory is automatic, cross-project, and retrieved by relevance." Practitioner evidence in §3–4 undercuts each half of that narrative in different ways.
- Evidence quality is low and self-referential: Engram's benchmark is on LOCOMO (conversational memory), and its "vs" table is authored by Engram; no third-party replication was found. Install counts measure distribution, not benefit.
- The most credible positioning is the one that concedes the weak points — Harbor's gate/retirement/counting framework and ClawMem's "only as good as what you index" — because those map onto the measured failure modes in §4.
- The ecosystem is actively inventing workarounds for *built-in* memory's limitations (truncation, startup-only loading, per-repo scope), which is itself evidence that the built-in implementations have real usability gaps.

### Gaps
- No independent third-party evaluation comparing these memory products on a coding benchmark was found.
- No pricing/traction/revenue data beyond self-reported npm install counts.
- Hindsight first-party materials could not be retrieved; only its existence as a competitor is confirmed.
- No data on security/privacy incidents (memory poisoning, leakage across repos) beyond the Harbor "agent memory poisoning" article title; that topic likely deserves separate research.
