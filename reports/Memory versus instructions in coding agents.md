# Memory Helps, but Availability Decides

Memory does help coding agents, but less than its advocates imply and not in the way the question assumes. The largest reported gains come from artificial recall tasks — MemGPT lifted GPT-4 deep-memory-retrieval accuracy from **32.1% to 92.5%** by paging full history in through function calls against a baseline that saw only a lossy summary ([Source](https://arxiv.org/abs/2310.08560)) — while on real software work the same idea buys only a few points: Chronos raised mean SWE-bench Verified resolution from **69.2% to 72.9%** across six backbones, with SWE-bench Pro rising 48.3% → 51.7% ([Source](https://arxiv.org/abs/2610.11578)). The more reliable payoff is cheaper, shorter work rather than more correct patches: ContextSniper cut tokens **36–52%** and cost on SWE-bench while submitted-resolution rates differed by **one task out of 50** ([Source](https://arxiv.org/abs/2607.01916)). What actually decides success is whether the right, correct fact is available at the moment of action — a controlled study across seven models and five harnesses found that supplying a missing API fact restores success, withholding it costs exactly the work it supports, and distance from the edit is irrelevant ([Source](https://arxiv.org/abs/2608.16630)). On short histories, simply putting the whole history in the prompt beat commercial memory products (**0.9184 vs 0.5773**), so memory's genuine niche is scale: beyond the context window, across sessions, and under token budgets ([Source](https://arxiv.org/html/2410.10813v2)). Instruction files are not a rival mechanism so much as the other half of the same one — a human-written, always-loaded form of memory that is good enough for short, stable rules but degrades with length, staleness, and conflict, and that neither it nor agent memory actually enforces ([Source](https://code.claude.com/docs/en/memory)). The honest answer is settled as a design pattern and open as an experiment: every major vendor ships both, yet no controlled trial has shown either wins on coding-task success.

## Synthetic recall gains shrink to a few points on real code

The case for memory looks overwhelming until the benchmarks are read closely. MemGPT's headline **+28 to +58 accuracy points** on deep memory retrieval came from a task designed to reward exactly what a memory system does — recalling a specific past fact from a long multi-session chat — where the baseline was handicapped with a recursive summary of the prior five sessions ([Source](https://arxiv.org/abs/2310.08560)). Nested key-value retrieval made the contrast starker: GPT-4 and GPT-4 Turbo fell to **0% accuracy by three nesting levels**, while MemGPT with GPT-4 was unaffected up to four ([Source](https://arxiv.org/html/2310.08560v2)). But the same literature shows the ceiling. On the 97-question LongMemEval subset, long-context models given the whole 115k-token history lost **30–60% of accuracy** relative to being given only the evidence sessions, and commercial memory assistants scored 0.25–0.71 where offline reading of the full history scored 0.9184 ([Source](https://arxiv.org/html/2410.10813v2)). Structured organization — graphs, multi-key indexes, time awareness, reflection synthesis — reliably beats flat vector retrieval, but typically by **single digits to about ten points**: A-MEM raised temporal F1 from 18.41 to 45.85 on LoCoMo yet *lowered* adversarial F1 from 69.23 to 50.03, and with GPT-4 single-hop accuracy fell from 61.56 to 48.43 ([Source](https://arxiv.org/html/2502.12110v11)). Gains are real but non-uniform across question types.

On coding tasks specifically the evidence is thinner and younger than the marketing. The cleanest result, Chronos, distills merged pull requests into structured "experience cards" linked by a typed graph and applies them on top of SWE-Agent, producing the **69.2% → 72.9%** gain on SWE-bench Verified, a 48.3% → 51.7% gain on SWE-bench Pro, and 41.0% → 43.5% on FEA-Bench Lite; a human evaluation found graph-grounded retrieval surfaced **2.87 useful cards versus 1.24** for flat semantic retrieval out of ten fetched ([Source](https://arxiv.org/abs/2610.11578)). MemGuard, which persists verifier outputs as lifecycle metadata so that memory admission is validated, won its success metric in **all 16 backbone-benchmark settings** tested, with gains of 2.4–7.9 success-rate points over the strongest prior memory baseline ([Source](https://arxiv.org/abs/2608.21867)). Against those, a multi-language harness study found **two null regions** — gains appeared only where there were recoverable execution defects, and approached zero where defect mass was near zero ([Source](https://arxiv.org/abs/2608.10178)). Every direct SWE-bench memory result in this literature is a **2026 preprint**, most with only the abstract verified, so they should be read as strong recent signals rather than settled science ([Source](https://arxiv.org/abs/2610.11578)). The closest peer-reviewed coding result remains Reflexion's within-task episodic reflection, which reached **91% pass@1 on HumanEval versus 80%** for the prior GPT-4 state of the art — trial-and-error inside one task, not persistent memory of the user ([Source](https://arxiv.org/abs/2303.11366)).

What distinguishes the helpful cases is *what is stored*: merged PRs, prior patches, learned file-writing behavior, and validated failure signals — structured, checkable, task-relevant artifacts — rather than prose about a user's life ([Source](https://arxiv.org/abs/2610.11578)). A line of work trains the agent to write and read its own files as memory across context replacements, with small 4B and 9B models reported competitive with much larger Qwen3.5 models on SWE-bench Verified and MLE-bench Lite, and learned file-memory behavior transferring to Terminal-Bench 2.1 and SWE-Bench Pro V2 ([Source](https://arxiv.org/abs/2609.34422)). Where memory helps coding agents, then, it helps as procedural and episodic scaffolding around the code, not as a personal long-term recollection, and the consistent benefit is efficiency and reach rather than dramatic accuracy ([Source](https://arxiv.org/abs/2607.01916)).

## Availability at the moment of action decides outcomes

The most direct answer to the user's question comes from an experiment that holds the agent fixed and varies only whether a needed fact is present. Supplying and withholding required facts across seven models and five harnesses showed that **no model completes a task on an unseen API with both channels empty, and putting the facts in the prompt restores success**; the paper's operative finding is that "availability decides the outcome and distance does not" ([Source](https://arxiv.org/abs/2608.16630)). The same study found harnesses that all passed every test differed **more than tenfold in tokens consumed** because they rebuilt the same content at different rates — and that spending more recovered nothing when the facts were withheld ([Source](https://arxiv.org/abs/2608.16630)). This reframes the debate: the choice between memory and instructions is a choice about *where a fact lives*, when success turns on *whether the fact is there and correct*. A short, correct prompt can beat a sophisticated memory system; a stale one is worse than nothing, because an available-but-wrong fact makes the agent act on it and produce plausible-looking but wrong code ([Source](https://arxiv.org/abs/2608.16630)).

Two strong results cut against the "just put it in the prompt" conclusion, and both are about scale. Offline reading of a complete short history with GPT-4o scored **0.9184** on LongMemEval versus 0.5773 for ChatGPT's memory and 0.3299 for Coze's, with authors concluding the result "highlights the gap between building a seemingly personalized chat assistant by recalling isolated facts and demonstrating a genuinely strong memory ability" ([Source](https://arxiv.org/html/2410.10813v2)). Yet the same paper measured **30–55% accuracy drops** across GPT-4o, Llama 3.1 70B and 8B, and Phi-3 when the full 115k-token history was supplied, with "Lost in the Middle" supplying the mechanism — performance peaks at the beginning and end of a long context and degrades in the middle even for explicitly long-context models ([Source](https://arxiv.org/html/2307.03172)). The working-set study adds a coding-specific wrinkle: on SWE-bench, where models likely already know the repositories, reads no longer predict success because **parametric memory substitutes for both prompt-provided and retrieved facts**, so the availability question has a third channel beyond prompt and store ([Source](https://arxiv.org/abs/2608.16630)).

Controlled comparisons that fix the wording find that memory structure itself adds value. A-MEM explicitly held **identical system prompts** for all baselines and its own method, so its F1 differences are attributable to memory organization rather than better instructions ([Source](https://arxiv.org/html/2502.12110v11)). Chronos layered its PR memory on top of an existing SWE-Agent scaffold and still added 3.7 mean points, and its two experience-guided *single-agent* variants also beat the base agent, indicating memory alone carried part of the gain ([Source](https://arxiv.org/abs/2610.11578)). Recent self-evolution work points the same way but with a warning: gated modular evolution of harness components beats **prompt reflection** specifically on SWE-bench Lite, while full-harness rewrites and prompt bloat are flagged as failure modes alongside benchmark gaming and evaluator tampering ([Source](https://arxiv.org/abs/2611.22299)). The synthesis across all of this is that the research supports neither "memory beats instructions" nor "instructions beat memory" as a blanket claim — for a codebase, a durable AGENTS.md-style instruction file is itself a form of memory with the same failure modes of staleness, conflicting authority, and silent over-reading ([Source](https://arxiv.org/abs/2608.16630)).

## Instruction files are memory with the same failure modes

The measured evidence on instruction files is genuinely mixed, and the two controlled studies optimize different things. Lulla et al. ran a paired within-task design over **10 repositories and 124 pull requests** with Codex and gpt-5.2-codex and found AGENTS.md cut median wall-clock time from 98.57s to 70.34s (**−28.64%**) and median output tokens from 2,925 to 2,440 (**−16.58%**), both statistically significant — but they explicitly did **not** evaluate correctness, calling task-completion behaviour "comparable" and labelling the work "a first step" ([Source](https://arxiv.org/abs/2601.20404)). The more rigorous ETH Zurich / LogicStar study built AGENTbench from **138 instances across 12 Python repositories** and concluded that "providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average," holding across models, agents, and both generated and developer-committed files; instructions were "well followed," yet repository overviews — popular and recommended by providers — were "not helpful," while files were useful for specifying non-standard coding practices ([Source](https://arxiv.org/abs/2602.11988)). Secondary reporting of an earlier version gives a more differentiated picture — human-written files around **+4%** success, LLM-generated files −0.5% to −3% — and attributes the difference to **redundancy** with existing README/docs, a version-drift conflict worth flagging ([Source](https://academy.dair.ai/blog/agents-md-evaluation)). Both studies are narrow, both are 2026, and neither covers large refactorings, multiple languages beyond Python, or multiple agent families in one design ([Source](https://arxiv.org/abs/2602.11988)).

Vendor guidance and the measured mechanism agree on what to put in these files. AGENTS.md is a tool-neutral format adopted by **60,000+ projects** and stewarded under the Linux Foundation, with explicit precedence rules — the closest file to the edited file wins, explicit user chat prompts override everything, and large monorepos use nested files ([Source](https://agents.md/)). Anthropic recommends **under 200 lines per CLAUDE.md** because "longer files consume more context and reduce adherence," advises concrete rules over vague ones, and supplies `/doctor prompt-audit` to catch instructions written for older models, dead file references, and contradictory files ([Source](https://code.claude.com/docs/en/memory)). GitHub's analysis of **2,500+ agents.md files** found executable commands placed early, one real code example over three explanatory paragraphs, and three-tier "Always do / Ask first / Never do" boundaries ([Source](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/)). The ETH result that overviews are useless fits what context-engineering research predicts: an overview is a distractor-rich, low-signal block competing for an attention budget already stretched by code and tool output ([Source](https://arxiv.org/abs/2602.11988)).

The limitations are structural, not just authoring mistakes. Claude treats CLAUDE.md as **context, not enforced configuration**, so contradictions are resolved probabilistically — "Claude may pick one arbitrarily" — and `@path` imports expand together with the importing file rather than reducing its context cost ([Source](https://code.claude.com/docs/en/memory)). "Lost in the Middle" and Chroma's "context rot" report show why growing a file backfires: performance degrades with input length even on simple tasks, even one distractor hurts and four compound, logically structured haystacks perform *worse* than shuffled ones across all 18 models tested, and focused ~300-token prompts beat full ~113k-token prompts across every model family ([Source](https://research.trychroma.com/context-rot)). Anthropic frames context as "a finite resource with diminishing marginal returns" governed by an "attention budget," and notes that Claude Code's CLAUDE.md files are "naively dropped into context up front" while glob/grep retrieve files just in time ([Source](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Vendors' own answer — path-scoped rules, on-demand skills, subagents, hooks, compaction, memory — is a set of retrieval and caching layers around instruction files, an implicit admission that injecting everything every session does not scale ([Source](https://code.claude.com/docs/en/memory)). Instruction files have their own measured weakness too: a trace of 557 agentic sessions and 33,097 agent PRs found instruction files were **60.5% of documentation interactions** but the probability a consultation was followed directly by an edit was **0.002**, and a check of 481 public CLAUDE.md files found only **4–16%** of security rules mapped to an enforcing control, leading the author to call CLAUDE.md "a write-only channel" ([Source](https://gethrbr.com/blog/do-agents-need-memory)). So "just use AGENTS.md" is not a complete answer either.

## Injected experience helps; autonomous recall mostly does not

The sharpest empirical finding — and the one closest to a direct memory-versus-instructions comparison — separates *supplying* past experience from asking a memory system to *choose* it. VibeMemBench built 111 coding targets from 90 real repositories, each paired with past experience **verified to help**, and found that directly injecting that experience raised task resolution of **four of five held-out solvers by 1.1 to 4.5 points** and cut steps for all five; but when four existing memory systems had to build and retrieve the experience from the same history themselves, **eleven of twelve solver-and-system pairings failed to beat the same agent with memory off** ([Source](https://gethrbr.com/blog/do-agents-need-memory)). This is reported at abstract level through a vendor's synthesis and needs primary verification, but it aligns with the broader pattern: what memory systems *select* is the weak link, not the existence of past experience. Governance is decisive — MemGuard's gains of 2.4–7.9 points come from validating what enters memory, and its failure taxonomy names "failed trajectories, accidental successes, and misleading observations" that enter because they appear relevant, plus banks that "accumulate duplicate, stale, and conflicting records that retrieval alone cannot repair" ([Source](https://arxiv.org/abs/2608.21867)).

Staleness is measured, not hypothetical. In a shared-memory false-belief study, once an uncontested false belief entered the store the answering agent asserted it in **97–99% of probes** across four agent families; gating on declared source type cut false adoption to **6–9%** versus 22–47% under other policies, while deduplicating sources "rejected true claims along with the false ones" ([Source](https://gethrbr.com/blog/do-agents-need-memory)). A companion study loaded five agent-memory systems with a revoked policy and its replacement and found **none enforced the revocation by default** — the revoked fact came back wherever retrieval could see it, outranked its replacement, and led agents to the unsafe action ([Source](https://gethrbr.com/blog/do-agents-need-memory)). A working-set study adds the coding-specific danger: a stale convention file is **worse than no file**, because agents follow the standard even when it prescribes worse code, and a missing fact produces wrong work rather than absent work because the agent fabricates the file or guesses the value ([Source](https://arxiv.org/abs/2608.16630)). Retrieval also degrades with volume: A-MEM's sweep over 10 to 50 retrieved items found gains "gradually plateau and sometimes slightly decrease," as richer context introduces noise ([Source](https://arxiv.org/html/2502.12110v11)), and MemGPT "will often stop paging through retriever results before exhausting the retriever database" ([Source](https://arxiv.org/html/2310.08560v2)).

Practitioner sentiment tracks the same split by *kind* of persistence. Kevin Liao's "Agents don't need memory, they need documentation" reached the Hacker News front page with **369 points and 281 comments**, arguing that memory plugins "retrieve snippets by similarity, without context, with stale facts treated as current, and nobody can audit them" ([Source](https://liao.gg/blog/agents-dont-need-memory)). But the recurring counter-objection is that a markdown folder has the same unknown-unknowns problem — the agent still has to guess which page matters — and that whatever is written needs enforcing because prose rules get broken anyway ([Source](https://gethrbr.com/blog/do-agents-need-memory)). The dominant practitioner pattern is not "memory vs no memory" but "small, human-owned, path-scoped context vs large, agent-owned, similarity-retrieved context," with complaints about bloat, silent truncation, double-loading, and staleness flowing from *how much* text is injected and *who validates it* rather than from persistence itself ([Source](https://news.ycombinator.com/item?id=47593178)). The commercial picture is asymmetric: the vendors with the widest deployment — Anthropic, Cursor, Cline — attach **no outcome measurements** to their memory or rules features, while third-party memory products publish self-run numbers on conversational-recall benchmarks such as LOCOMO rather than on "did the agent ship a better patch" ([Source](https://www.engram.fyi/compare)). No vendor has published a controlled trial showing its memory feature beats its own instruction-file mechanism on coding success, tokens, or time ([Source](https://code.claude.com/docs/en/memory)).

## The dividing line is time, provenance, and non-derivability

The reason the binary dissolves is that every major vendor's persistent mechanism is ultimately a text file injected into context; the only architectural difference is *who writes it and how it is selected* ([Source](https://code.claude.com/docs/en/memory)). Claude Code ships both: **CLAUDE.md** is written by the user, holds instructions and rules, is version-controlled, and loads every session; **auto memory** is written by Claude, holds learnings and patterns across worktrees, loads through the first 200 lines or 25 KB of a `MEMORY.md` index, and is typed into `user`, `feedback`, `project`, and `reference` categories ([Source](https://code.claude.com/docs/en/memory)). Critically, auto memory "skips anything it can derive from the codebase" and "also skips anything your CLAUDE.md files already say" — an explicit statement of the non-derivability boundary ([Source](https://code.claude.com/docs/en/memory)). Cursor goes further and ships **no autonomous memory store at all**, saying "large language models don't retain memory between completions" and providing only rules, with the best-practice advice to "start simple" and "add rules only when you notice Agent making the same mistake repeatedly" ([Source](https://cursor.com/docs/context/rules)). The shared trigger heuristic across vendors is the same: a correction repeated twice, or a fact a new teammate would need, earns promotion into durable guidance ([Source](https://code.claude.com/docs/en/memory)).

Memory becomes necessary at three boundaries rather than at a single threshold. **Time:** "each new session begins with no memory of what came before," and compaction alone is insufficient, so Anthropic's long-running-agent harness has an initializer write `init.sh`, a progress file, and a structured feature list that the coding agent reads at each session start — with the paper stating that "getting agents to make consistent progress across multiple context windows remains an open problem" ([Source](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)). **Provenance and non-derivability:** structured notes written outside the window and read after resets enable long-horizon behavior such as a Pokémon agent tracking tallies across thousands of steps, which "would be impossible when keeping all the information in the LLM's context window alone" ([Source](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). **Scope and enforcement:** machine-local memory is not shared across machines, and hard rules belong in PreToolUse hooks or managed `permissions.deny` settings, not in guidance prose ([Source](https://code.claude.com/docs/en/memory)). Large codebases matter less as a trigger than accumulating state: a big repo is handled by just-in-time retrieval, while many sessions with unresolved decisions, inferred preferences, and half-finished features demand memory ([Source](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

That is why the question is best answered as **settled as a design pattern, open as an empirical question**. Practitioners broadly agree on the division of labour, and context engineering has absorbed memory as one primitive among compaction, tool-result clearing, rules, skills, and subagents on one finite attention budget — the cookbook advice is to "start with the one that matches the bottleneck you're actually observing" ([Source](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)). But the measured case for any particular configuration is weak, version-dependent, and framed differently by each study: the ETH authors say attempts to improve performance "should be rigorously evaluated before deployment," Lulla et al. call their work "initial empirical evidence," and Fowler describes a field in a "storming phase" where "we can never be certain of anything" ([Source](https://arxiv.org/abs/2602.11988)). No direct memory-versus-instructions A/B exists, no study measures how fast a convention file goes stale, and no independent replication of vendor memory benchmarks was found ([Source](https://gethrbr.com/blog/do-agents-need-memory)).

## Conclusion

The useful reframe is that neither mechanism is a truth source — both are text injected into a finite attention budget, and both fail the same way when the text is stale, redundant, or wrong. The emerging design lesson treats reliability as a supply-chain problem for facts: gate what enters, enforce retirement on read, deliver facts with the task, count what was actually used, and move hard rules into controls rather than prose ([Source](https://gethrbr.com/blog/do-agents-need-memory)). On the evidence available, the highest-value move is not "add memory" but "inject the right verified experience at the right time" — the one intervention that has been shown to lift solvers consistently — and autonomous semantic recall currently destroys more of that value than it creates ([Source](https://arxiv.org/abs/2608.21867)).

For the practical decision, instructions are good enough for short, stable, always-true, team-shareable rules, and adding memory there costs tokens without buying correctness ([Source](https://arxiv.org/abs/2602.11988)). Memory earns its place for facts that cannot be expressed that way — a decision made on a specific date, a preference inferred from corrections, the state of a half-finished feature, a cross-session progress log — and for histories that outgrow the context window or the token budget ([Source](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)). The open problem is no longer whether to keep notes but how to keep them honest across sessions, which is where the next decisive evidence will come from.
